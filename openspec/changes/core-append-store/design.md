# Design

## Context

仓库为空，只有 `DESIGN.md`（总体设计）。动机与范围见 proposal.md。技术栈已由总体设计确定：Cloudflare Workers + Turso (libSQL)，目标是免费额度内长期运行。本 change 只覆盖文本的写入路径，不含查询、向量、附件。

已确认的前置决定（来自 explore 讨论）：
- 每个库对应一个独立的 Turso 数据库，一条 SQL 不跨库。
- 记忆 ID 由内容确定，使同一条记忆提交到多个库时 ID 相同，并且重试幂等。
- meta 是灵活的 JSON，不参与 ID，因此可按库脱敏、可随时增删字段。

## Goals / Non-Goals

**Goals:**
- 一个可部署的最小闭环：`mem append` → Worker → Turso，幂等、可鉴权、dev/prod 隔离。
- 定下后续 change 都依赖的契约：记录字段、ID 规则、meta 约定、schema_v。
- 所有核心逻辑（规范化与 hash、校验）能在本地不依赖云端测试。

**Non-Goals:**
- 不做 SQL 查询、FTS、向量、`embed()`（后续 change）。
- 不做附件、OCR、提交页、反馈与维护流程。
- 不做用户管理或 token 轮换界面；token 以 secret 配置，手工轮换即可。
- 不做删除与更新；这是流水账的设计约束，不是遗漏。

## Decisions

### 1. 记录的存储形态：核心列 + `meta` JSON 列
`memories` 表的核心字段用真实列，`meta` 用 JSON 文本列。

- 理由：meta 要求可自由增删字段；SQLite/libSQL 有 JSON 函数，可直接按字段过滤。常用字段将来可在派生层提升为列并建索引，派生表可整体重建，因此无需现在预判哪些字段会热。
- 备选：meta 拆成 EAV 子表。查询繁琐、写入放大、rows written 成倍增加，免费额度下不划算，放弃。
- 备选：meta 全部设为固定列。每加字段就要迁移，违背“灵活增删”的要求，放弃。

### 2. ID 算法：对核心字段规范化后取 sha256 前 128 位，base32 编码
输入为 `ts`、`author`、`kind`、`content`、附件 sha256 列表（本 change 暂无附件，保留位置）。规范化采用键排序的确定性 JSON 序列化，`ts` 统一为 UTC 毫秒精度的 ISO 字符串。

- 理由：128 位对个人规模碰撞概率可忽略；base32 便于人和 agent 复制；`meta` 不参与，使 meta 可按库脱敏与随时演进。
- 备选：随机 ULID。需要服务端协调才能保证跨库同一条记忆的 ID 一致，且重试不幂等，放弃。
- 备选：仅对 `content` 取 hash。内容相同而时间或作者不同的记录会被误判为同一条，放弃。
- 权衡：同作者、同毫秒、同内容的两次写入会被视为同一条。这是预期行为（见 spec 的幂等要求）。

### 3. 规范化与 ID 计算放在共享包，CLI 与 Worker 同时使用
CLI 在客户端生成 `id`，Worker 收到后用同一份代码重算校验。

- 理由：避免两边实现漂移；不一致就拒绝，可以尽早暴露 bug 与篡改。
- 同时在仓库里放一组固定的 ID 测试向量（输入与期望输出），后续任何语言的客户端都以此作为兼容基准。

### 4. 幂等：以 `id` 为主键，冲突即忽略
插入采用“若不存在则插入”的语义，返回是否新写入；既有记录不被覆盖，`received_at` 与 `meta` 保持首次写入值。

- 理由：与只追加原则一致，重试安全。
- 备选：`ON CONFLICT DO UPDATE` 合并 meta。会改写已有记录，违背只追加，放弃。

### 5. 库与 token 的映射：token 在配置中绑定到唯一库
Worker 从 secrets 读取“token → 库（Turso 地址 + 凭据）”映射，请求先鉴权再取库连接。token 比较使用常数时间。

- 理由：每库独立 DB 时，隔离的关键就是 token 到库的绑定；个人规模下静态映射足够，无需引入账户体系。
- 备选：把映射放进一个元数据库。多一次网络往返与一个额外的单点，当前规模不需要。

### 6. 客户端 `ts` 与服务端 `received_at` 分离
`ts` 由 CLI 生成并参与 ID，`received_at` 由 Worker 写入、不参与 ID。

- 理由：重试必须复用同一个 `ts` 才能幂等；`received_at` 仍保留“服务端何时收到”这一事实，便于排查时钟偏差。

### 7. meta 采集与清洗在 CLI 端完成
CLI 采集后，对每个目标库应用该库的脱敏配置（如不记录 `cwd`），再各自发送；因为 meta 不入 ID，各库 ID 保持一致。

- 理由：Worker 不应看到不该写入某个库的信息；清洗必须发生在数据离开本机之前。
- git remote 的 userinfo 一律移除，清洗失败则省略该字段，宁缺毋滥。

### 8. 迁移机制：版本化 SQL 文件 + `schema_v`
schema 以顺序编号的 SQL 文件管理，部署时对每个库幂等执行；记录的 `schema_v` 取写入时的版本。

- 理由：流水账不可改写，所以迁移只允许新增列或表，不允许改写旧记录。

### 9. 测试与部署分层
- 本地：用本地 libSQL 文件库加 wrangler 本地模式，覆盖 ID、校验、幂等、鉴权、多库隔离、CLI 重试。
- 部署：dev 与 prod 各一套（独立 Worker、独立 Turso DB、独立 token）。完成本 change 后在 dev 做首次冒烟（真实 Turso 凭据、token、CLI 指向真实 URL），再部署 prod。
- 理由：基础设施风险（secrets、网络、Turso 凭据）只能在真实环境暴露，越早越好。

## Risks / Trade-offs

- [ID 规范化实现不一致导致两端 hash 不同] → 共享包加固定测试向量；不一致时 Worker 拒绝，错误信息指明哪个字段不同。
- [客户端时钟偏差使 `ts` 不准] → `received_at` 作为旁证；不在写入时纠正 `ts`，避免破坏幂等。
- [同毫秒同内容被合并] → 视为预期；如以后发现真实场景需要区分，可在核心字段中加入客户端生成的 nonce，那将是 ID 规则的版本升级，需要新 `schema_v`。
- [meta 采集泄露敏感信息] → CLI 端清洗 + 按库脱敏配置 + 采集失败则省略；将敏感信息样例纳入测试。
- [token 泄露] → token 只存在于本地配置与 Worker secrets，不进日志与输出；个人规模下手工轮换，轮换流程写入部署文档。
- [Turso 免费额度] → 本 change 仅文本追加，估算用量远低于上限；`rows written` 随后续派生表增加，再由后续 change 评估。
- [多库提交不是原子的] → 不做分布式事务；各库独立幂等，CLI 报告每个库的结果，失败的库可用相同命令安全重试。
